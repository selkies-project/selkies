# PixelFlux 2.2.0

A release that drives every codec through its own library with no FFmpeg, keeps long-term references in every encoder that has them so each client recovers from a loss without a key frame, cleans up a still screen from its content under Turbo and constant rate alike, adds 10-bit encoding, and hardens the Computer Use, recording, and camera sockets, with a switch that keeps each software session on one thread for hosts that run many.

## Breaking Changes

- **Computer Use requires a bearer token** : the server does not start without one (`PIXELFLUX_CU_TOKEN`, or the token passed to `start_computer_use`), and every request has to carry it as `Authorization: Bearer <token>`. A loopback port is open to every account on the host and to any page open in the session's own browser, and the server drives the session with its owner's full authority. A caller that takes screenshots or injects input over it sets the token
- **A named recording is written only inside `PIXELFLUX_RECORD_DIR`** : `/record_start` takes a file name inside the directory the operator gives callers, written owner-readable and never through a link, into a file this user alone owns
- **The camera and recording sockets serve their user alone** : a socket another account owns is refused, the camera socket defaults to the runtime directory, and its frame ring is sealed against writes from the peer
- **`ScreenCapture.app_screen_control_available` is `app_screen_control_offered`** : whether the app compositor serves KWin's screencast virtual outputs, read from its registry without touching a screen
- **No FFmpeg** : VA-API is driven through libva and every software codec through its own library (x264 or OpenH264, x265 or kvazaar, libvpx, SVT-AV1), so the wheels link no libavcodec

## New Features

- **10-bit encoding** (`CaptureSettings.video_bit_depth`, 8 or 10) : on VA-API (HEVC, VP9, AV1), NVENC (HEVC, AV1), and in software (x264, x265, libvpx VP9, SVT-AV1), a GPU that lacks the format handing the session to the software encoder. `pixelflux.hardware_formats(encode_node_index, auto_gpu)` names the formats each codec's engine encodes: `"420-8"`, and beside it `"444-8"`, `"420-10"`, and `"444-10"` where the engine takes them
- **Long-term references for every client** (`CaptureSettings.acknowledge_references`, `ScreenCapture.acknowledge_reference`) : NVENC, libvpx, SVT-AV1, VA-API H.264 and H.265 (on radeonsi), and OpenH264 pin the newest anchor every client holds and predict their anchors from a frame they were all sent, so each client of a shared stream recovers from a loss of any depth on its own, without a key frame
- **`CaptureSettings.video_reference_frames`** : caps the reference frames an H.264 or H.265 stream keeps
- **`CaptureSettings.cpu_encode_threading`** (default `True`) : off, each software encoder codes a frame on one thread and the striped encoders code their stripes one after another, bounding what one capture takes of a host that runs many; the `Encoder:` line names the threads
- **`ScreenCapture.update_link_rate(kbps)`** : the rate the transport measures its path at, which a still screen's constant-rate cleanup may run at
- **The vblank rate for the X server** : the capture's frame rate is published on the root window, `_FAKE_SCREEN_FPS` and to the millihertz `_FAKE_SCREEN_MILLIHZ`, for an X server that paces its fake vblank by it, so a vsynced application presents as fast as it is streamed
- **The DRI3 blit waited for on the GPU** : behind a semaphore an X server offering `SELKIES-SEMAPHORE` signals after the blit, so an encoder queues behind it at once rather than after a CPU round trip
- **Wayland input and pointer** : `inject_finger_scroll` and `inject_finger_scroll_end` scroll as a touchpad does, with the stop that starts kinetic scrolling; `pointer_location` reports where the compositor's pointer is and which injected moves that includes
- **Clipboard** : `clipboard_served_app` reports which flavors an app compositor's selection served to pasters
- **Reports** : the capture says whether the display server offered the encoder a zero-copy path, and keeps each window's fastest, slowest, and largest frame

## Encoding & Pipeline

- **A still screen cleaned up from its content** : one policy reads what changed from compositor damage, the X server's report, or a content hash (on the GPU where NVENC uploads the frame or NvFBC captures it), under Turbo as in any mode; under a constant rate a still screen is refined to the paint-over quality whatever the switch says, and a cleanup that stalls sweeps its bands at the paint-over quantizer
- **NVENC** : AV1 frames split across the encode engines in strips, and HEVC ones from 4K; a Turbo frame's bands hashed on the device beside its encode
- **VA-API** : the driver's fastest quality level; one slice a picture on AMD's VCE; coded bytes copied straight into the framed output
- **H.264 streams bound reordering at zero**, written back into the SPS where a device drops it
- **x265** : 8x8 coding units, reopened on a quality or rate change its live reconfigure never applies, and its constant-rate filler kept off the wire
- **VP8 in eight token partitions**, for a software decoder to thread across
- **One frame held at a quantizer whatever the rate control**, for every encoder

## Resilience & Fixes

- **Camera** : OpenH264 carried with a flush that returns the picture's buffer; H.264 scalable extension units ignored; a VP9 picture deeper than 8 bits and a JPEG claiming a picture no camera sends refused
- **NvFBC** declined where libX11 calls another copy of libxcb than the driver's
- **The recorder** dates an audio page's packets back from its granule across a producer's gaps
- **Computer Use** bounds what a request may send before its token is checked, and a refused request's answer reaches its client
- Further fixes across NVENC, the pipeline, VA-API, Wayland, X11, SVT-AV1, and libvpx
