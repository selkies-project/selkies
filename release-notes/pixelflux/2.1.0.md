# PixelFlux 2.1.0

A feature release adding a virtual camera for client webcam uplinks, resolving the software H.264 encoder at build time, and reworking the NVENC and host-capture paths for lower latency, alongside a full license inventory of both build configurations.

## Breaking Changes

- **`CaptureSettings.output_mode` is replaced by `CaptureSettings.codec`** : the integer mode (`0` JPEG, `1` H.264) becomes a codec name: `"jpeg"`, `"h264"` (striped, or full-frame with `video_fullframe`), or a full-frame video codec `"h265"`, `"vp8"`, `"vp9"`, `"av1"`; an unknown name raises `ValueError` at capture start. The Python `StripeFrame.data_type` is now the codec id (`0` JPEG, `1` H.264, `2` VP8, `3` VP9, `4` AV1, `5` H.265), the same ids `VirtualCamera.CODEC_*` carry
- **Video wire header** : the type byte of a `0x04` frame packs the codec id into its high nibble (`1` H.264, `2` VP8, `3` VP9, `4` AV1, `5` H.265) and the frame kind into its low nibble (`1` key, `2` intra, `0` delta), so a payload names its own codec and a client decodes whatever arrives without out-of-band state. Every encoder frames through one shared header writer
- **`ScreenCapture.active_codec()`** : the codec a capture streams once its pipeline is built, on X11 and Wayland alike, so a caller learns of a demotion the selection ladder made and can tell its clients
- **`pixelflux.SOFTWARE_ENCODERS`** : a dict from codec name to the software encoder the build carries (`"x264"` or `"openh264"` for H.264, `"x265"` or `"kvazaar"` for H.265, `"libvpx"` for VP8 and VP9, `"svt-av1"` for AV1), fixed at build time and each opened on a frame in a forked child once, so a codec whose encoder cannot run on the machine is absent; `pixelflux.SOFTWARE_FULLCOLOR` lists the codecs that encoder takes a 4:4:4 session for, and `pixelflux.hardware_fullcolor(encode_node_index, auto_gpu)` those the encode node's engine does, from the same probe as `hardware_encoders`
- **`video_min_qp` / `video_max_qp` / `video_crf` are a quality index on the H.264 QP scale** for every codec: each backend maps them onto its own quantizer domain: H.26x takes the index as its QP, while the VP8 quantizer index and the VP9 / AV1 `base_q_idx` come from tables measured against x264 at the same index (matched on SSIM over a captured desktop, and ramped to the codec's maximum quantizer at the top of the index where those encoders cannot degrade as far as x264), so one `video_crf` means one quality whichever codec streams; an NVENC AV1 session takes its own curve, matched on SSIM against H.264 on Ada, the metric the generations agree on
- **The recording socket carries the codec's own elementary stream** : Annex-B for H.264 and H.265, an OBU temporal-unit stream for AV1, IVF for VP8 and VP9; the MP4 recorder still takes H.264 only and rejects other codecs at start
- **Computer Use server binds loopback by default** : `PIXELFLUX_CU=<port>` and `start_computer_use("<port>")` now listen on `127.0.0.1,::1` only; comma-separated `host:port` entries name the addresses to listen on, `0.0.0.0:<port>,[::]:<port>` for every interface
- **`use_openh264` setting removed** : the software H.264 encoder is now chosen at build time, not per capture. The default `gpl` feature encodes every CPU H.264 session with x264; a `PIXELFLUX_ENABLE_GPL=0` build (`--no-default-features --features openh264`) encodes them with Cisco OpenH264 instead. `use_cpu` is once again purely the caller's software/hardware choice
- **`ScreenCapture.set_clipboard` takes `(mime, data)` entries** : the compositor's offer serves one payload per flavor, so a client pasting rich text takes the markup and one pasting into a plain field takes the text the source wrote, instead of both taking whichever flavor was picked for them. The plain-text entry is still advertised under all five conventional target names, and `text/html` joins the read preference so a copy made inside the session is seen as markup when its source offers it

## New Features

- **X11 zero-copy GPU capture (NvFBC)** : on an NVIDIA GPU whose session encodes on NVENC, the X11 path no longer goes through shared memory. The NVIDIA X driver composites each frame into a buffer it owns in video memory and hands back a CUDA device pointer, which is registered with the encoder in place and reused for the life of the geometry, so a frame is never read, written, or copied by the CPU between the screen and the bitstream — the property the Wayland dmabuf path already had. The session runs in push model, so the driver generates a frame when an application damages the screen rather than on a sampling timer, grabs take a waiting frame without blocking, and a fullscreen unoccluded application may present straight into the capture buffer, bypassing the X server. Measured at 1920x1080 on a Tesla V100 against the XShm path on the same display: 2.51 ms per frame instead of 5.24 ms for H.264 and 3.03 ms instead of 5.69 ms for H.265, with the host CPU under 0.2 ms a frame. It is selected automatically, and a session it cannot serve (a codec NVENC has no engine for, software encoding, a non-NVIDIA encode node, a watermark, or a driver without NvFBC) says so once and streams through XShm as before
- **X11 zero-copy GPU capture (DRI3)** : on any X server whose screen lives on the GPU (XLibre's Xvfb with glamor and DRI3, an Xorg on a DRM driver), the server blits the root into dmabufs pixelflux allocated through GBM on the server's own render node, and NVENC or VA-API encodes them in place through the Wayland zero-copy import. The cursor and the watermark are composited by the server through Render, so neither costs a readback. The server's DAMAGE report both says a frame is worth encoding and ends the wait for one, so a change is published as it lands: measured at 1920x1080 and 60 fps on an RTX 5000 Ada, a repaint reaches the encoder 3.8 ms after it is drawn instead of 8.8 ms, for no measurable CPU on either side. Chosen after NvFBC and before XShm, declined with one line saying why, and never a setting.
- **H.265, VP8, VP9, and AV1** : every video codec runs on NVENC (H.264, H.265, AV1), on VA-API (all five, with the low-power entry point some Intel generations require), and on the software encoder the build resolves for it: x265 (or kvazaar in a GPL-free build) for H.265, libvpx for VP8 and VP9, SVT-AV1 for AV1, each linked directly (`encoders/hevc.rs`, `encoders/vpx.rs`, `encoders/svtav1.rs`). One selection ladder (`select_frame_encoder`) serves X11, Wayland zero-copy, and Wayland readback: the hardware backend the encode node's driver names, then the codec's software encoder, then, for a codec with no path at all, the other video codecs the host serves, hardware first, striped H.264 after them, and JPEG last, each step with a logged reason, so a codec the machine cannot serve never leaves a black screen. Every backend keeps the same posture: infinite GOP with key frames on request only, no B-frames or lookahead, single-frame latency, parameter sets on every key frame, CBR with a one-and-a-half-frame VBV or a constant quantizer, 4:4:4 where the codec carries it (H.264 and H.265). libvpx VP9 is the one encoder given more than a single tile: one column per 256 pixels of width, the narrowest tile VP9 allows, which takes a third off its encode time for under three percent of bitrate at equal quality
- **Reference invalidation on every codec** : `invalidate_reference` predicts past a frame a client lost on every session whose encoder lets it name its references, not on NVENC and libx264 alone. libvpx VP9 runs in its flexible reference mode and addresses its eight buffer slots like a decoded picture buffer; libvpx VP8 keeps its three buffers on a schedule (LAST every frame, GOLDEN and ALTREF by turns every twelfth, so one anchor is always twelve to twenty-three frames old) and recovers from the newest anchor a client still has, with no entropy update carried across frames so a lost frame leaves no probability context behind; the VA-API session writes the H.264 and HEVC slice headers itself where the driver takes them packed, so a delta names a reference other than the newest and a reference picture set leaves the lost frames out, and addresses VP8's buffers and VP9's and AV1's slots through the picture parameters. A Tegra H.265 session names its references through the vendor's external reference set on L4T R32 and R36. A constant-rate SVT-AV1 session on a release that takes reference commands (4.2 on, which the wheels build) has the library store the same anchors and predicts past a loss from one of them. x265, kvazaar, and a constant-quantizer or earlier SVT-AV1 session offer nothing to steer and keep answering with a key frame, as do Tegra's H.264 and AV1 sessions and the stateful V4L2 ones
- **VA-API drives libva directly** : the VA-API session (`encoders/vaapi/`) speaks to libva itself, loaded at run time from the host, with bindings generated from the libva 2.24 headers the `va-sys` crate vendors: one arm per codec writes the sequence, picture, and slice parameters and, where the driver takes them packed, the H.264 SPS/PPS/slice, HEVC VPS/SPS/PPS/slice, and AV1 sequence and frame headers (`encoders/bits.rs`), with the rate control, quality level, slice layout, surface negotiation, and video-processor color conversion FFmpeg's `*_vaapi` encoders and `scale_vaapi` performed. A stand-in driver (`vaapi/mock.rs`) checks every buffer a session renders without hardware
- **FFmpeg is gone** : nothing in pixelflux links or loads libavcodec, libavfilter, or libavutil any more. The software encoders are linked directly and bound at build time from the headers of the copies that are linked (`codec-sys`: libvpx, x265 or kvazaar, SVT-AV1), so a struct layout that moves between releases never goes stale; the virtual camera decodes H.264 through OpenH264, VP8 and VP9 through libvpx, AV1 through dav1d, and HEVC through libde265. A build needs no FFmpeg of any version, and a GPL-free build is GPL-free whichever distribution's codec packages it links
- **NVENC is codec-parameterized** : the device's engine list decides which codecs open (AV1 is refused with a message on GPUs before Ada), HEVC and AV1 get the same rate control, VUI, and level pinning H.264 had, and AV1 keeps a single tile since tiles cost bitrate and buy no quality
- **VA-API readback converts on the GPU** : the Wayland readback path hands NVENC and VA-API the packed rows it holds (BGRA or RGBA) and both convert in hardware, so the encode thread runs no color conversion for a hardware session
- **Virtual Camera** : new `VirtualCamera` / `VirtualCameraSettings` classes turn a client's webcam uplink into a V4L2 capture device for applications. Encoded frames of any supported codec (H.264, VP8, VP9, AV1, HEVC, MJPEG) are pushed with `cam.push(buffer, codec, keyframe=...)` and decoded off the GIL on the camera's own thread; a browser sending JPEG is passed through as an MJPEG device with no decode. `push()` returns immediately and signals `KEYFRAME_WANTED` when the decoder needs an IDR, and `VirtualCamera.shm_layout()` reports the ring's byte layout for the interposer ABI test
- **Virtual-camera sinks** : the decoded stream is served to the Selkies V4L2 interposer over a shared-memory ring (no privileges), and mirrored to a `v4l2loopback` output device and a PipeWire `Video/Source` node where those are available (`libpipewire-0.3` is loaded at run time; there is no build-time PipeWire dependency)
- **Cursor delivery cap** : `cursor_size_cap` defaults to 128 on both backends, the most a browser shows as a cursor, so an application's own sprite (a game's 128px pointer) travels whole instead of being downscaled to the theme's size; larger sprites are still downscaled to the cap
- **KWin session screens** : a nested KWin session's screens are grown and removed on demand as `zkde_screencast_unstable_v1` virtual outputs (`add_app_screen`, `remove_app_screen`, and `app_screen_control_available`, which proves the rung by growing a probe screen and giving it back, since a stock KWin serves the request without registering the output), each held open by its own connection for as long as the screen should exist, and arranged through `kde_output_management_v2` (`set_app_screen_layout` falls through to it where `zwlr_output_management_v1` is absent); their scale follows the capture output's, which the host window's preferred fractional scale carries. The KDE output protocols are vendored under `protocols/`, newer than the copies the `wayland-protocols-plasma` crate bundles, because KWin sends a mode `flags` event those copies do not know
- **OpenH264 striped encoding** : in a `PIXELFLUX_ENABLE_GPL=0` build, OpenH264 now backs the striped path as well as full-frame — one encoder instance per stripe, with the same per-stripe wire header as x264 — so striped and full-frame sessions, CRF and CBR, and live bitrate/quality changes all work without libx264

## Encoding & Pipeline

- **NVENC direct dmabuf registration** : on the Wayland zero-copy path, capture dmabufs are registered with NVENC in place (pitch-linear as a device pointer, 4-channel surfaces as CUDA arrays) rather than copied per frame with `cuMemcpy2D`; set `PIXELFLUX_NVENC_DIRECT=0` to fall back to the copy path
- **Packed readback upload with hardware colorspace conversion** : the readback (non-zero-copy) NVENC path uploads packed BGRA/RGBA and lets the encoder's fixed BT.601 conversion do the work, cutting per-frame encode-thread CPU on that path
- **Shared primary CUDA context** : NVENC sessions on one device share a single primary CUDA context and query device caps up front (a 4:4:4 request the device cannot honor downgrades to 4:2:0, and a size past the device limit falls back to software with a clear message)
- **x264 reopens on an fps change** so its VBV and bitrate track the new frame budget instead of drifting
- **x264 CRF takes a VBV cap** : a positive `video_vbv_multiplier` under CRF caps the software x264 session at a peak of `video_bitrate_kbps` with that buffer (x264's capped CRF), so a key frame is bounded by the link it has to cross while the rate factor still picks the quality; with the multiplier at 0, CRF stays uncapped
- **Encoder settings chosen by measured latency** : VP8 runs at libvpx speed 16 (a fifth faster than speeds 8 to 14, which share one path, at the same quality), VP9 at speed 8 with screen tuning (a third faster than 7), SVT-AV1 at preset 11 in its real-time mode (`rtc=1`, a quarter faster than preset 10 and the mode SVT designates for real-time low delay; the presets above 11 are no faster), and NVENC at preset P3 (an H.264 frame in 3.7 ms against 5.2 ms at P4 on a V100 for a thousandth of SSIM, with two-pass quarter-resolution rate control kept because a single pass overshoots CBR by up to twelve percent and adaptive quantization moves nothing). The VP8, VP9, and AV1 quantizer tables were re-measured at those settings
- **VP9 carries 4:4:4** as profile 1 on libvpx (1.13 on) and VA-API, at the limited-range BT.601 signal of its 4:2:0, so `video_fullcolor` reaches every codec that has a 4:4:4 profile the browsers decode
- **Host frames reach VA-API without a copy** : the upload filter reads the capture's own rows, and the software encoders' color conversion runs on the rayon pool instead of spawning threads per frame
- **One color matrix on every backend** : every 4:2:0 session — NVENC, VA-API, and the software encoders — converts with BT.601 at limited range and declares it (BT.709 primaries and transfer, SMPTE 170M matrix), the matrix NVENC's hardware conversion is fixed at and the one browser presentation paths invert exactly; Chromium and Firefox paint a BT.709-tagged frame with a BT.601-like inversion, which put the software and VA-API streams up to 12 levels off on saturated color. The software 4:4:4 sessions stay BT.709 at full range

## Resilience & Fixes

- **Relative pointer motion under a nested KWin session** : KWin's nested backend turns the host seat's motion into absolute-only events, so a game holding a pointer grab under a KWin session (SDL through Xwayland's relative device, or any `zwp_relative_pointer_v1` client) saw no mouse movement while the desktop pointer worked. When the app compositor named by `set_app_wayland_display` advertises `org_kde_kwin_fake_input`, `inject_relative_mouse_move` now delivers each delta through that device, which enters KWin's delta path, followed by the seat's absolute move to the same position so KWin's pointer, the composited cursor, and the reported position stay aligned even after KWin repositions its pointer on a screen change; buttons and scrolling keep riding the seat, and a compositor without the global (wlroots forwards the seat's relative motion itself) is unaffected. KWin advertises the global to unprivileged clients only with `KWIN_WAYLAND_NO_PERMISSION_CHECKS` set
- **x264 and x265 never freeze part of the picture under a rate budget the content cannot meet** : both encoders default to a quantizer ceiling above the H.264/HEVC maximum of 51, an "emergency" range that exists only to force macroblock skips when the VBV underflows; on a screen stream that left rows of the picture on old content for a few frames after every oversized frame, seen as a one-slice seam. The CBR sessions now cap the quantizer at 51 (or the configured `video_max_qp`), so an impossible budget overshoots briefly instead, as NVENC and libvpx do
- **Host-capture layout is applied without blocking the event loop** : layout requests to an external compositor are submitted non-blocking and reconciled on a later tick against a ledger, so a resize or teardown no longer stalls the calloop; a host that keeps its own mode (a refusal, no output-management protocol, or no answer by the deadline) has the capture re-sized to the mode it actually runs, and the refusal becomes a `capture_state` caveat
- **A canceled screen configuration is rebuilt rather than refused** : `zwlr_output_configuration_v1` cancels whatever is in flight when the compositor's own state moves, which is the same moment a screen is arriving or leaving. That says the serial went stale, not that the plan was rejected, so the configuration is rebuilt against the new state for as long as a time budget allows; a session screen's mode and scale applied while screens change no longer fall back to a capture-side scale
- **A display's tracker follows its screen's scale** : a display cut from a screen kept the scale its damage tracker was built with, so a live DPI change drew the session at the old scale until the display was resized: magnified into a corner after a change down, a quarter of the screen after a change up. The tracker is rebuilt when the screen's scale changes, as it already was when the display's size did.
- **A pointer bound late is entered at once** : a client that binds `wl_pointer` while the pointer already rests on its surface (a rootful Xwayland, a toolkit that binds lazily) now gets the enter at bind, where it got none until the pointer moved and its first motion and click reached a pointer it had never entered
- **The pointer follows a window that maps or closes under it** : pointer focus moved only with the pointer, so a window opening over a still pointer, or the window on top closing, left a click that arrived with no motion first (a pointer-locked one) on the window no longer shown there; the compositor now hands the pointer to what lies under it whenever a window maps, unmaps, or moves
- **The virtual camera ignores H.264 scalable extension units** : a prefix NAL unit, subset SPS, or extension slice naming a layer above the base turned OpenH264 to a layer that never arrives, so it decoded nothing again, key frames included, while the camera asked the client for a key frame on every push; those units are dropped before the decoder, as an AVC decoder does
- **Wayland pipeline time starts at the composite** : a frame's `pipeline_ns` on the Wayland paths counts from the composite that samples the clients' buffers, as the X11 figure counts from its grab, where the zero-copy path counted from the encode start and left the composite out
- **An X11 capture takes control requests while it starts** : its first frames reach the callback before `start_capture` returns (a DRI3 capture names its encode thread only once its first frame is out), and what a consumer asked for in reply was dropped until the capture was published: a frame it lost, a key frame, a rate, a tunable, the region, cursor compositing, and a stop, which the capture then outlived. Selkies' video bridge names a frame it lets go at capture start, and under an infinite GOP an encoder that never hears of it keeps predicting from it. The requests now reach the capture from the moment its threads spawn, and a stop in that window ends it before it is published
- **NVENC predicts past a loss older than its recent frames** : an H.264 or H.265 session whose device invalidates references keeps long-term frames as anchors (H.264 the key frame and every 48th frame, H.265 two, every 12th by turns), so a loss a receiver reports after the frames its level's buffer holds (four at 1080p in H.264) is answered with a prediction from an anchor rather than a key frame, and a resize to a smaller picture stays in place instead of reopening the session
- **Surface-backed cursors are answered on commit** : pixelflux now services the frame callback of a client's cursor surface and delivers the sprite when it commits, fixing frozen cursors for Xwayland and libwayland-cursor clients under host capture
- **`capture_state(display_id)`** reports `(state, last_error)` and records why a pipeline went down (no output, host connect failure, encoder fallback, a refused GBM resize, host death); `get_realized_geometry` returns `None` on a genuine timeout rather than a stale size
- Bgr888 shared-memory frames swap red and blue per the wire format so client color is correct on that path

## Build & CI

- **Wheels build the codec libraries from source** : libvpx, SVT-AV1, dav1d, and libde265 on every wheel, x264 and x265 on the GPL wheel, and kvazaar on the non-GPL one, and bundle them; no FFmpeg and no libva are built, the wheel's VA-API session opening the host's libva at run time and asking it for nothing a 2.13 release does not export. The test and docs workflows and the devcontainer take the distribution's codec development packages in place of a conda FFmpeg
- **Software H.264 is a build-time license switch** : the default build links GPL-2.0-or-later `libx264`; `PIXELFLUX_ENABLE_GPL=0` substitutes the BSD-licensed, vendored OpenH264 and pulls in no copyleft component. A notice at install time states which posture was built
- **License inventory** : `LICENSES.md` documents every crate and native library — linked, vendored, and run-time-loaded — of both the default (`gpl`) and `PIXELFLUX_ENABLE_GPL=0` builds. `scripts/check-licenses.py` and `pixelflux/deny.toml` gate both configurations, run by the new `Licenses` workflow; a crate that links, loads, or vendors native code must be described before the check passes
- **Minimum Rust raised to 1.89**
- **Oldest codec libraries a source build takes** : libvpx 1.11, x265 3.5, kvazaar 2.3.2, SVT-AV1 1.0, dav1d 1.0, and libde265 1.0.8; an older one stops the build at its pkg-config probe with the library and the release it needs
- The OpenH264 crates are dependencies of every build, since their decoder is the virtual camera's H.264 decoder, so the OpenH264 encoder's tests run under the default build too (`cargo test --lib`, and `cargo test --lib --no-default-features --features openh264` for the GPL-free graph)
